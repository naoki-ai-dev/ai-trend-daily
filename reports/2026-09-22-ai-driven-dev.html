総論：焦点は「作らせる」から「暴走させない」へ

  • 直近の記事群で目立つのは、コード生成そのものの話題ではなく、エージェントに権限をどう与え、出力をどう検証するかという運用設計の議論である。
  • 「AI 開発元の減速宣言」を扱った記事は、機能追加の速度に対して安全装置が自動的に追従してくるわけではない、という構造を指摘している。ツール提供側のペースと、利用側が自分で用意すべきガードレールを切り分ける視点が共有されつつある。
  • 結果として、権限設計・完了判定・評価基準という三つの領域に議論が集中している。いずれも「エージェントが正しく動いたことを人間側がどう確認するか」という同じ問題の別の側面である。

権限とサンドボックス：設定だけでは守れない

  • Claude Code で Bash("rm*") を deny 設定しても実際にはファイルが削除されるという報告は、許可リストの設定だけに依存する運用の危うさを具体例で示した。パターンマッチによる拒否は回避経路が残りやすく、実行環境そのものの隔離が必要になる。
  • 自作 MCP サーバーに認証と権限スコープを導入する事例では、3 層の分離設計によって危険なツールを呼び出せないようにする手法が紹介されている。MCP がツール接続の標準として広がるにつれ、サーバー側で権限を持つ設計責任が明確になってきた。
  • API や MCP が未整備な Web サービスをブラウザ経由で自動操作する「Browser Operator」の設計論も出ている。操作対象がクリック可能な UI 全体に及ぶため、何を許可し何を人間に戻すかの線引きが安全性の核心になる。
  • 共通するのは、権限を「設定ファイルの記述」ではなく「アーキテクチャ上の境界」として実装せよ、という方向性である。宣言的な deny だけでは実行時の抜け道を塞げない。

完了判定と「黙って間違う」問題

  • エージェントの「しました」という報告を信じて 2 回壊した経験から、完了の定義を 3 つに分けて決めたという記事は、自己申告を成果物として受け取らない運用の必要性を示している。
  • UI 自動化の検証記事は、15/15 で通ったテストが反復実行では誤読を起こすという現象を記録している。決定的に失敗するのではなく、確率的に、しかも静かに間違うため、単発の成功が品質の保証にならない。
  • この「黙って間違う」性質は、従来のテスト観と相性が悪い。成功率が高いほど検証を省きたくなるが、失敗が可視化されないぶん実害は後工程に回る。
  • 対策として、完了条件を人間が事前に言語化し、エージェントの主張とは独立した検証手段を持つ、という設計が繰り返し推奨されている。

評価設計：何を Green とするか

  • Agent Eval に関する記事は、評価の技術的な実装よりも「何を成功とみなすか」を決めることが難しい、という点を主題に据えている。エージェントの出力は自由度が高く、正解が一意に定まらない場面が多い。
  • 判定基準そのものを、人間が後から却下した実データから引き直した事例も報告されている。「ok の理由」に書いた抽象語が抜け穴になり、基準が形骸化していたという指摘は、評価プロンプト設計の具体的な失敗モードを示す。
  • 抽象語による合格基準は、モデルにとって都合よく解釈できる余地を残す。評価基準は具体的な観測可能事象に落とし込む必要がある、という教訓が共通している。
  • 完了判定・UI 検証・Eval 設計はいずれも、エージェントの自己評価を信用しないための仕組みづくりという点で連続している。

指示を「実行保証」に近づける

  • SKILL.md に書いたのに実行されない、という問題に対し、「お願い」から「実行保証」へ近づける 5 つの設計を提示した記事がある。指示の記述場所だけでなく、記述の強度と検証可能性が論点になっている。
  • エージェントを放置すると全件ダンプするという指摘は、それがトークン量の問題ではなく、必要な情報を絞り込む判断をしていないことの表れだと整理している。コンテキスト設計は節約ではなく判断の委譲の問題として扱われつつある。
  • 指示の書き方に関する議論は、プロンプトエンジニアリングから、ツール定義・スキル・権限を含む実行環境全体の設計へと範囲を広げている。

ハーネスとモデル選択の多様化

  • 複数のコーディングエージェントを 1 つのチームとして扱うメタハーネス AgentEngine の事例は、特定ツールへのロックインを避ける方向の動きを示す。Claude Code、Codex、Qwen といった異なる実装を横断的に扱う需要が出てきた。
  • Z.ai による ZCode の公開は、コーディングエージェントのハーネス自体が独立したプロダクト領域になっていることを裏づける。モデルとハーネスが分離して競争する構図が明確になってきた。
  • Claude Haiku 4.5 への切り替えで踏んだ落とし穴の報告は、モデル変更がコスト最適化だけでは済まないことを示す。同一ハーネス上でもモデル差が挙動の差として表面化するため、切り替え時の再検証が必要になる。
  • ハーネスが抽象化層として成熟するほど、どのモデルをどのタスクに割り当てるかという配分設計が実務上の主要な意思決定になる。

実務への示唆

  • 権限設計は設定ではなく境界として実装し、削除やネットワークアクセスなど不可逆な操作は実行環境レベルで隔離する。
  • エージェントの完了報告は入力として扱い、独立した検証を必ず通す。特に成功率の高いタスクほど静かな失敗を見落としやすい。
  • 評価基準は抽象語を避け、却下事例から具体化する。基準を決める作業自体が評価システムの中心的コストである。
  • モデルとハーネスの選択肢が増える一方、切り替えコストは検証負荷として跳ね返る。乗り換えの容易さと再検証の手間を合わせて判断する必要がある。
