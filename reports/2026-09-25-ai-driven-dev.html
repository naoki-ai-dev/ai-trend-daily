AI駆動開発の動向

📅 2026-09-25 ⏱ 約10分で読めます 🗂 7トピック

概況

  • 2026年9月下旬のAI駆動開発は、新モデルの投入と開発ツールの仕様変更が重なり、変化の速い時期にある。
  • 実務の関心は「AIに何をさせるか」から「AIをどう統制し、どう安全に運用するか」へ移りつつある。
  • 本レポートでは、モデルとプラットフォームの動向、Claude Codeの仕様変化、フックによるガードレール、仕様駆動の開発プロセス、セキュリティ分野での応用の5つの観点から整理する。

モデルとプラットフォームの動向

  • 9月1日にClaude Fable 5.1とMythos 5.1が登場した。同一モデルに2段階のセーフガードを適用し、提供形態を出し分ける設計が注目されている。
  • この設計は、性能の向上と安全性の担保を同一モデル上で両立させる試みといえる。利用者は、自分の用途がどちらの提供形態に該当するかを意識する必要がある。
  • Claude APIの9月更新では、拒否応答への課金再開とCompliance APIの破壊的変更が報告されている。
  • 拒否応答が課金対象に戻ることで、プロンプト設計の良し悪しがコストに直結するようになる。Compliance APIを組み込んだ監査・ガバナンス系システムは改修が必要になる。
  • GPT-6系（Astra／Sol／Luna）とClaude Opus 5.5に同じアプリを作らせ、品質・所要時間・料金を実測で比較した検証も公開された。
  • ベンダー発表のベンチマークだけでなく、自分のユースケースで実測してモデルを選ぶ姿勢が広がっている。複数モデルを用途に応じて使い分ける前提が定着しつつある。

Claude Codeの仕様変化とエコシステムの標準化

  • Claude CodeがAGENTS.mdを読み込むようになったことが報告された。
  • AGENTS.mdはエージェント向け指示ファイルとして複数ツールで共有されている形式である。対応により、Claude Code専用の設定とCodexなど他エージェント向けの設定を一本化しやすくなる。
  • この変化は、特定ツールへのロックインを避け、同じリポジトリを複数のエージェントで扱う運用を後押しする。
  • Claude Code v2.1.282では、プロジェクト設定によるテレメトリの改ざんを防ぐ破壊的変更が入った。
  • リポジトリに含まれる設定ファイルが信頼できるとは限らないという前提に立ち、プロジェクト単位の設定で変えられる範囲を狭める方向の変更である。
  • 共有リポジトリや外部由来のコードをエージェントで扱う機会が増えるなか、設定ファイル自体が攻撃面になりうるという認識が製品設計に反映され始めている。

ガードレールの重心は「プロンプト」から「フック」へ

  • CLAUDE.mdに書いたルールが守られなかった件数を7日間記録し、その結果をもとにフックで機械的に拒否する方式へ切り替えた実践が共有された。
  • 自然言語の指示は確率的にしか守られない。確実に禁止したい操作はフックで決定的に止めるという使い分けが、実務の知見として固まりつつある。
  • 感覚ではなく、違反件数を数えてから対策を決めた点が重要である。ガードレール設計にも計測に基づく改善サイクルが持ち込まれている。
  • 別の記事は、Claude Codeが利用者のメールアドレスをコンテキストとしてモデルに渡している点を指摘している。そのうえで、この情報が外部に出ていく経路をフックで塞いだ事例を紹介している。
  • この事例は、エージェントが保持する個人情報や秘密情報を、外部送信の出口で機械的に検査するという発想を示している。
  • 両記事に共通するのは「モデルの善意や理解力に頼らず、実行環境側で強制する」という設計思想である。エージェントの自律性が高まるほど、この層の重要性は増していく。

開発プロセス：仕様の置き場所とオーケストレーションの見直し

  • AI駆動開発において、仕様をどこで、どこまで維持するかを論じた記事が公開された。
  • AIがコードを高速に書き換える環境では、コードだけを正とするとすぐに意図が失われる。そのため、仕様を開発の起点かつ拠り所として維持するスペックファーストの考え方が再評価されている。
  • 一方で、仕様を細かく書きすぎると維持コストが膨らむ。仕様として固定する範囲と、コードやテストに委ねる範囲の線引きが実務上の論点になっている。
  • 自作のエージェントオーケストレーション基盤を使わなくなった経緯を振り返り、モデルの進化とどう付き合うかを考察した記事もある。
  • モデル本体やツールの標準機能が進化すると、以前は必要だった自作の仕組みが不要になる。周辺の作り込みは短期間で陳腐化しうる。
  • このため、モデルの限界を補うための仕組みは「いずれ捨てる前提」で薄く作る姿勢が有効といえる。長期的な投資は、仕様・テスト・ガードレールのようにモデルが変わっても価値が残る領域に振り向けるのが合理的である。

セキュリティ分野での応用

  • GitHub Security Labは、Taskflow Agentを用いたAIによるファジングの取り組みを紹介している。
  • ファジングは、ハーネスの作成や結果の分析といった専門知識が必要な作業が多い分野である。エージェントがこれらを補助することで、脆弱性発見の裾野が広がる可能性がある。
  • AIの用途がコード生成にとどまらず、検証やセキュリティ評価といった品質保証の工程へ広がっていることを示す事例である。
  • 前述のフックによる情報流出対策と合わせると、AIは「守るべき対象」と「守るための道具」の両面でセキュリティに関わるようになっている。

総括と今後の注目点

  • モデル面では、セーフガードの出し分けやAPI課金体系の変更など、性能以外の要素がモデル選定に影響する局面に入っている。
  • ツール面では、AGENTS.md対応に見られる標準化と、設定改ざん対策に見られる信頼境界の明確化が同時に進んでいる。
  • 運用面では、プロンプトによる「お願い」から、フックによる「強制」へ統制手段が移行している。違反の計測に基づいて対策を選ぶ姿勢も広がっている。
  • プロセス面では、仕様を拠り所とする開発と、陳腐化を前提とした周辺ツールの設計が、モデルの急速な進化への現実的な対応策になっている。
  • 今後は、破壊的変更への追従コストをどう抑えるか、複数エージェントを横断する統制をどう標準化するかが主要な論点になると考えられる。
