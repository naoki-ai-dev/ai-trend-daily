## 概観

- AI駆動開発の論点は、コードをどれだけ速く生成できるかから、エージェントをどう任せ、制御し、検証するかへ移りつつある。
- GitHub Blogがコード生成の先にある「agentic engineering」を開発者向けの主題に掲げたことは、この変化を象徴している。
- 現場の報告では、権限設定の思わぬ挙動、AIによる修正案の破損、検収工程でのトークン大量消費など、運用段階の課題が具体的に語られ始めた。
- 全体として、AIの能力そのものより、AIを組み込む開発プロセスの設計が成果を左右する段階に入っている。

## エージェントへの委任と権限制御

- GitHub Blogの「Beyond code generation」は、開発者向けのガイドとしてagentic engineeringを取り上げている。
- 「生成の先」が主題になったことは、AIを補完ツールではなく、開発工程を担う存在として捉える見方の広がりを示す。
- VS CodeのAgent Mergeでは、マージまでAIに任せるかどうかを3段階の設定から選べる。
- 委任の範囲を「全部か無か」ではなく段階的に選ぶ設計は、リポジトリの重要度やチームの成熟度に応じた導入と相性がよい。
- マージはコードが本流に入る最終関門であるため、どの段階を選ぶかは、ツールの好みではなくチームの統制方針として決める必要がある。
- `claude -p` の事例では、`--allowedTools` を指定しても道具は絞られず、定時ジョブの子プロセスにEditとShellが見えていたと報告された。
- この事例の教訓は、オプション名から受ける印象と実際の制御範囲を混同しないことである。
- 無人で動く定時ジョブは、人が途中で止める機会が少ない。設定した内容だけでなく、実行時にエージェントから何が見えているかまで確認することが重要になる。

## 品質保証とテスト設計

- GitHub ActionsとClaude Codeを組み合わせたCI/CDの検証では、AIレビューが仕込んだ問題をすべて見つけた一方、修正案の半分以上は壊れていた。
- この結果は、問題の検出と正しい修正が別の能力であることを端的に示している。
- 実務上は、AIレビューを指摘の網羅に活用し、修正案はテストと人の確認を通してから採用する分業が現実的である。
- AIエージェントのテスト設計に関する記事は、実行結果と判断過程をどう評価するかを論点に据えている。
- エージェントは同じ結果に異なる経路で到達し得るため、最終出力の正否だけでなく、途中の判断も評価対象に含める発想が求められる。
- レガシーPHPの記事は、AIに直させる前に特性テストを張らせる手順を扱っている。
- 既存の振る舞いを先にテストで固定しておけば、AIによる変更が挙動を壊したかどうかを判定しやすくなる。
- 3件に共通するのは、AIの出力を信じるかどうかではなく、検証できる仕組みを先に用意するという姿勢である。

## コストと生産性の測り方

- AIの検収担当が1回で885万トークンを使っていたという報告は、検証工程にもAIのコストが発生することを具体的な数字で示した。
- 品質を高めるためにAIによる確認を重ねると、その工程自体が大きなコスト要因になり得る。
- エージェントを多段に組む場合は、成果物の品質に加えて、工程ごとのトークン消費を監視する必要がある。
- 「人間3分、AI48分。これは何分の仕事か？」は、AI時代の工数をどう捉えるかという問いを投げかけている。
- 人の作業時間とAIの実行時間は同じ尺度で単純に比較できないため、見積もりや生産性評価の前提を見直す必要がある。
- 「意思決定だけで週100コミット積むAI開発手法」は、人の役割を意思決定に寄せて開発量を積み上げるアプローチを示している。
- この手法が示唆するのは、実装の担い手がAIに移るほど、人の仕事は何を作り、何を受け入れるかの判断に集中するという変化である。
- 一方でコミット数は開発量の指標にすぎないため、品質や手戻り、トークン消費と併せて評価することが欠かせない。

## 知識の持ち運びやすさ

- ChatGPTからの乗り換えで困らなかった理由として、知識をAIのメモリではなくgitに置いていたことを挙げる事例が報告された。
- AIサービス内のメモリに知識を蓄積すると、ツールの変更時に文脈を持ち出しにくくなるおそれがある。
- gitで管理すれば、知識を特定のサービスから切り離せるうえ、変更履歴も追跡できる。
- モデルやツールの入れ替わりが速い現状では、知識をツールの外に置くことが、ロックインを避ける実践的な手段になる。

## 今後の注目点

- 委任範囲の設計が重要になる。マージ権限のような影響の大きい操作は、段階的に任せ、チームとして基準を明文化することが望ましい。
- 権限は設定値だけで安心せず、実行環境で何が見え、何ができるのかを確認する運用が求められる。
- AIの提案をそのまま採用せず、特性テストやCIなどの機械的な検証を通す流れが標準になっていくとみられる。
- 評価指標は、コミット数や作業時間だけでなく、トークン消費、修正案の採用率、手戻りまで含めた多面的なものへ広げる必要がある。
- 知識や手順をリポジトリに残す習慣は、ツールが変わっても開発基盤を維持するための土台になる。
